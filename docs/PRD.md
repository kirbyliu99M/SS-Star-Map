## 0. 一句話與 TL;DR

**一句話**：讓一個很熟的小圈子，在需要的時候想得到、找得到、也請得動對的人，包括朋友的真朋友；再透過同時身在好幾個圈子的人，把一個個圈子接成星系。

- **產品四件事**：模組化個人網頁（門面）、浮游星圖（內圈自己人，外圈是大家的 connection）、人脈書櫃加引薦流程（真正解決問題的地方）、星光與謝禮（讓人情被記得）。
- **長期是生態系**：溫度留在圈內，觸及靠人跨圈。每個新圈出生時就帶著一條關鍵串連；關係長得夠厚、兩邊投票通過，星橋才會亮起（§12）。
- **三個不做**：不做動態牆、不賣給學校、不讓沒同意的人出現。
- **節奏**：創業驗證。首圈是 ≤ 15 人的比賽圈，Kirby 用 AI 單人開發；全屆在首圈驗證後半年到一年內上線；2027 下半年開放試點圈、測試跨圈連線。

## 1. 背景與問題

我們這屆累積了大量專長、經驗和外圈人脈，但這些資源只存在每個人的腦袋和 LINE 群組裡。需求一來（例如比賽急需某種專長），常常「想不到」對的人；事後才發現，如果當時有想到 Matt，結果可能不一樣。Kirby 自己過去 12 個月就發生 6 次以上；而他常一起比賽的 15 個人裡，他清楚對方會什麼的不到一半。

現有工具都只解決一半：

| 工具 | 解決了什麼 | 沒解決什麼 |
|---|---|---|
| LINE 群組 | 即時、都是熟人 | 問不到朋友的朋友；在幾十人的群組公開求救有心理門檻；誰會什麼只留在聊天紀錄裡；每個群組都是孤島 |
| LinkedIn | 公開履歷、弱連結 | 圈子太大、表演性高，很多人畏懼使用；看不到「我朋友的真朋友是誰」，也不是為「需要時找得到、請得動」設計的。台灣會員滲透率約 16–17%【多來源數字不一致】。浮游星不取代它，而是互補：LinkedIn 放公開履歷，浮游星放圈內的「我能幫你什麼、我正在找什麼、朋友怎麼說」；使用者可以把自己的 LinkedIn 輸出帶進來，當個人網頁的草稿（§9.5） |
| 個人 CRM（Clay/Mesh、Dex、Folk） | 個人記住人脈 | 只有個人視角，沒有群體信任，也看不到朋友的朋友 |
| 校友平台 | 大型名冊、導師媒合 | 太大、太官方，跟 LinkedIn 一樣是「陌生人的目錄」 |
| 品牌頁／Link-in-bio（HypeLink、Linktree） | 好看的個人門面 | 每個人的頁面各自獨立，沒有圈子、沒有關係 |

**問題陳述**：一個高信任的小圈子，缺少一個可搜尋、會更新、尊重同意的方式，在需要時找到圈內和「圈內人認識的人」擁有的能力與資源，並透過信任的人完成引薦。

研究依據（詳見 v0.1 研究報告）：Science 2022 年針對 2,000 萬 LinkedIn 用戶的實驗發現，「中等弱連結」最能帶來新工作；同學轉介研究顯示，經由同學找到的工作薪資較高、較少離職。外圈之所以有價值，正是因為它要透過內圈的信任才能用。

## 2. 產品原則

1. **長出新圈，不撐大舊圈。** 每圈軟上限 150 人。要變大就開新圈，新圈透過創圈的人連回原本的圈（§12）。Path 一路放寬好友上限，最後失去了定位。
2. **同意才出現。** 任何外部的人，沒有按下 email 裡的同意，就不會出現在任何人的畫面上。
3. **目錄，不是動態牆。** 不做按讚、追蹤數、瀏覽數。沒有東西需要表演。
4. **情感是資料。** 「我們怎麼認識的」、朋友替你寫的介紹、一起經歷過的事，是書櫃裡最可信的證據，也是 LinkedIn 給不了的溫度。
5. **填一次，到處用（mass customization）。** 同一份資料同時長成個人網頁、星圖上的星、書櫃條目、LINE 名片。
6. **資料可以帶走。** 個人網頁可以匯出靜態檔，資料可以匯出 JSON。就算平台消失，也不會帶走你的東西（Bento、Read.cv 關站的教訓）。
7. **美感是入口。** 大家願意填資料，是因為想要一個好看的網頁。設計品質本身就是功能。
8. **人情記在心裡，不攤在桌上。** 星光帳本只有自己看得到；公開的是感謝的話，不是數字。不替幫忙開價（§11）。
9. **溫度在圈內，觸及靠人。** 跨圈要先有兩邊投票開通的星橋，而且只能經由人轉達；沒有全站搜尋、沒有陌生人名錄（§12）。
10. **外部平台只是資料來源與出口，不是資料庫。** 與 LinkedIn 等外部平台的整合，只接受使用者自己取得、自己上傳、自己確認的**本人資料**，或使用者自己貼的連結。不爬取、不匯入他人名單、不代發文；任何一筆進來的資料，都要經過使用者逐項確認才寫入。

## 3. 目標、非目標、成功指標

### 3.1 目標

| ID | 目標 |
|---|---|
| G1 | 需求出現後 48 小時內，讓需求方找到至少一位可行人選或引薦路徑 |
| G2 | 首圈（≤ 15 人）「書櫃搜尋可用日」（S9）起 90 天內，至少 10 人用過書櫃搜尋（P3 Gate 當天只有約 8 週資料，【待決】檢視日是否延到 06/15）；圈內找人需求中，至少一半先查書櫃、不是先問 LINE |
| G3 | 首圈每人平均 ≥ 5 項「我可以幫你」、≥ 3 位外圈連結或牽線標籤 |
| G4 | 零筆外圈資料在未經同意下出現；個資申訴 100% 依法處理 |
| G5 | 2027 年底前生態系有 3 個以上的圈、至少 2 座星橋開通，並完成至少 3 次跨圈引薦 |
| G6 | 全屆在首圈驗證後半年到一年內，以第二個圈的形式上線 |

### 3.2 非目標

- 不賣給學校或組織，不做校友名冊、會員 CRM。
- 不做動態牆、按讚、追蹤數、瀏覽數。
- 不做公開註冊後就能搜尋陌生人。
- 不匯入通訊錄；不匯入 LinkedIn 的人脈、聯絡人、訊息，也不匯入 LinkedIn 資料副本（ZIP）；不爬取 LinkedIn，也不使用代爬的第三方資料服務；不用 LinkedIn API 代使用者自動發文。
- LinkedIn 只透過三種方式整合：使用者自己貼的連結；使用者自己上傳**本人**的 LinkedIn「存為 PDF」或履歷 PDF（§9.5）；使用者自己按下的分享。
- 不做廣告、不賣資料、不讓招募方付費看人。
- 不做付費諮詢、不替幫忙開價；感謝一律在事後、自願（§11）。
- 不做公開求救板（Ask 板）；求救走私下搜尋加一對一引薦。
- 不做全站搜尋或陌生人名錄；跨圈只能經由人轉達（§12）。
- 2027 年 6 月前不做：原生 App、平台經手金流。

### 3.3 成功指標

| 指標 | 定義 | 目標【假設】 | 開始看的時間 |
|---|---|---|---|
| **北極星：需要時回來用** | 圈內「找人」需求中，先查書櫃的比例（每月一題問卷「這個月怎麼找人的」＋系統紀錄） | ≥ 50% | P2 起 |
| 90 天搜尋覆蓋 | 上線 90 天內用過搜尋的成員／全圈 | ≥ 10/15 | P2 起 |
| 成功引薦數 | 雙方同意聯繫，且請求方回報「有幫助」 | 首圈每月 ≥ 3 則 | P1 起 |
| 引薦成功率 | 成功／已發出 | ≥ 40% | P3 |
| 需求到首個可行人選時間 | 中位數 | ≤ 48 小時 | P1 |
| 外圈同意率 | 預先邀請、需要時才邀分開算：同意／已送達 | 預先邀請 ≥ 50%；需要時才邀應更高 | P1（人工測） |
| 書櫃密度 | 每人平均「我可以幫你」、外圈連結＋牽線標籤 | ≥ 5、≥ 3 | P2 |
| 謝禮率 | 回報「有幫助」的引薦中，事後送出謝禮的比例 | 觀察，不設目標 | P3 |
| 星橋 | 開通數、提案通過率、每座星橋上的跨圈引薦數 | 2027 年底 ≥ 2 座 | P5 |
| 跨圈引薦 | 經由星橋完成的跨圈引薦 | 2027 年底累計 ≥ 3 則 | P5 |
| 新圈來源（生態系飛輪） | 新圈中，創圈者原本就在某個圈（成員或外圈）的比例 | ≥ 50% | P5 |
| 資料新鮮度 | 12 個月內確認過的資料占比 | 上線 12 個月後 ≥ 50% | P5 |

**成立標準**：Kirby 決定不設停損點，所以前兩項（北極星與 90 天搜尋覆蓋）就是「這件事成立」的判斷依據，在 P3 結束時檢視。只看每月活躍會冤枉這個產品：找人本來就是需要時才用，15 人全圈每月大約只有 7 次需求。

**護欄指標**

| 指標 | 門檻 |
|---|---|
| 未經同意出現的外圈資料 | 0 |
| 個資申訴處理 | 法定 30 日內 100% 處理完畢，平台目標 7 日 |
| 請求集中度 | 前 10% 成員承接的請求 ≤ 40%（避免少數人被消耗） |
| 封鎖與檢舉 | 單一圈每季 > 3 件時，平台主動關心 |

## 4. 使用者與角色

### 4.1 Persona

| Persona | 描述 | 需要什麼 | 怕什麼 |
|---|---|---|---|
| P1 門面型（小安） | 準備求職或創業，想要一個好看的個人網頁 | 15 分鐘做出像樣的頁面，讓圈友知道自己能做什麼 | 在 LinkedIn 自吹自擂；沒時間架站 |
| P2 救火型（Kirby） | 常參加比賽與黑客松，臨時需要特定專長 | 快速找到「誰會 X」或「誰認識會 X 的人」 | 想不起來誰會；不好意思冷訊息 |
| P3 資源型（學姐） | 工作 1–3 年，有產業人脈 | 有選擇地幫忙，不被大量請求淹沒 | 被當工具人；請求品質參差 |
| P4 外圈（Matt） | 不是圈內成員，是成員的朋友或同事 | 知道自己被記錄什麼，自己決定要不要被找到；幫了忙會被記得；加入對自己也有用 | 未經同意被曝光；陌生人打擾 |
| P5 圈主 | 開圈並維護的人 | 低負擔管理成員、入會與爭議 | 一個人扛全部；畢業後沒人管 |
| P6 平台管理員 | 我們自己 | 審核開圈、處理升級案件、看全平台健康度 | 人力有限 |
| P7 橋星（跨圈人） | 同時在兩個以上圈子的人，例如同時在比賽圈和全屆圈 | 幫兩邊牽線時被看見、被感謝 | 變成兩邊的轉達機器 |

## 5. 核心情境與 User Stories

### 5.1 八個情境

**A. 開圈。** 首圈由平台直接建立，不走申請。Kirby 把 14 位常一起比賽的夥伴拉進「比賽圈」（暫名），並設定第二位圈主。3 步精靈帶他填基本資料、改圈規樣板、貼上 email，按下開圈。畫面上，第一顆星亮起。

**B. 15 分鐘建好個人網頁。** 小安收到邀請信，輸入 6 位數驗證碼登入。她上傳自己的履歷 PDF，系統拆成「經歷」「作品」「我可以幫你」三個區塊草稿。她刪掉兩項、補上一項，選了「星夜」主題後按發布。她的星在星圖上變亮，個人網頁網址是 `/@anan`。

**C. 邀請外圈 Matt。** Kirby 在「我的星座」按「邀請外部朋友」，輸入 Matt 的 email，寫一句「大學專題夥伴，碳盤查超強」，勾選要顯示的欄位。Matt 收到 email，看清楚是誰邀請、哪個圈、圈內 15 位成員會看到什麼，再按同意（不用註冊）。這時他才出現在星圖外圈。

**D. 比賽急需專長，找到 Matt。** 週五晚上，阿哲的團隊報名永續金融個案競賽，週一要交件，沒人懂碳盤查。他在書櫃搜尋「碳盤查」，結果分兩群：圈內的小美「做過 ISO 14064 專題」，以及外圈的 Matt（經由 Kirby）。阿哲對 Kirby 發出引薦請求，寫明需求、時限和「為什麼找他」。Kirby 一鍵轉達，Matt 看完內容後同意，雙方拿到聯絡方式。比賽結束，阿哲回報：「有幫助，進決賽。」Matt 得到一顆幫忙星光、Kirby 得到一顆牽線星光；阿哲寫的那句感謝，在 Matt 同意後出現在他網頁的「朋友說」。結案頁問阿哲要不要送 Matt 一杯咖啡，他按下去，跳到 LINE 禮物。

**E. 半年更新。** 畢業半年後，圈主在 Console 按「發起更新」。每個人收到一封信，只有三題：工作有變嗎？新增了什麼專長？現在在找什麼？30 秒填完，星的亮度回來了。

**F. 低頻與休眠。** 圈子 180 天沒人登入，系統問圈主要繼續、交接還是封存。封存後圈子變唯讀，但每個人的個人網頁不受影響。

**G. 需要時才邀請。** 小美要找會 3D 列印的人。書櫃裡沒有圈內人選，但有一條「Kirby 能牽線：3D 列印」。Kirby 收到請求後，才寄同意信給他的高中同學，信裡直接附上小美的需求。對方同意後，才出現在圈裡，同時收到這則引薦。在這之前，系統裡沒有他的任何資料。

**H. 跨圈。** 2027 年秋天，Matt 用了半年，自己開了「永續顧問圈」，成為兩個圈之間的第一條關鍵串連。幾個月後又多了三條：Kirby 和兩位顧問圈成員互相確認認識，另一位比賽圈成員也加入了顧問圈。系統提示「可以提案開星橋」，兩個圈各自不記名投票通過，星橋亮起。阿哲又需要 ESG 揭露的專家，書櫃顯示：「在 1 個相連的圈子裡有人可能會，經由 Matt」。阿哲發出請求，Matt 在自己的圈裡轉達；對方同意後，雙方才看到彼此。

## 7. 開圈 Console：客戶第一次申請

> v0.3：首圈由平台直接建立，MVP 只做 3 步精靈與批次邀請；本章其餘流程在 P5 開放試點圈時才做。

### 7.1 流程總覽

```
官網「申請開圈」
  → 申請表（約 5 分鐘）
  → 平台審核（48 小時內；首圈免審）
  → 核准信（附設定連結，7 天有效）
  → 設定精靈 7 步
  → 邀請創始成員
  → 開圈（第一顆星亮起）
  → 首週清單
  → 第 30 天回訪
```

### 7.2 申請表欄位

| 欄位 | 說明 | 必填 |
|---|---|---|
| 圈子名稱 | 例如「台科企管 2027」 | ✓ |
| 圈子類型 | 同屆／比賽隊伍／社團／前同事／家族／其他 | ✓ |
| 你們怎麼認識的 | 一段話描述共同經歷。審核最看重這一題 | ✓ |
| 預估人數 | 5–150 | ✓ |
| 共同圈主 | 第二位圈主的 email（至少 2 位，交接用） | ✓ |
| 想用來做什麼 | 多選：找人幫忙、畢業後保持聯繫、互相展示、其他 | ✓ |
| 入會方式 | 只能由管理員邀請／成員可以提名加擔保 | ✓ |
| 同意事項 | 圈規基本原則、外圈同意制、不得用於招募推銷 | ✓ |
| 怎麼知道我們的 | 通路歸因 | 選填 |

### 7.3 審核標準與時效

- **核准條件**：真實關係（不是陌生人社團或行銷名單）；人數 ≤ 150；至少 2 位圈主；用途不是商業招募、直銷或政治動員。
- **試點期優先**：已有線下互動、有明確共同經歷的圈子。
- **時效**：P5 起 48 小時內回覆；不核准時說明原因，可以補件。
- **後續**：由既有圈主擔保的申請可自動核准（P6）。

### 7.4 設定精靈（7 步）

| 步驟 | 內容 | 設計重點 |
|---|---|---|
| 1. 基本資料 | 名稱、一句話、圈子徽記（emoji、顏色或小圖） | 徽記會出現在成員的星與個人網頁上 |
| 2. 星圖外觀 | 星空樣式、主色 | 即時預覽 |
| 3. 入會規則 | 管理員邀請／成員提名加擔保（0、1、2 人）；人數上限（預設 150） | 用白話解釋每個選項的後果 |
| 4. 預設可見度 | 新成員各區塊的預設可見度 | 預設保守：「我的圈子」 |
| 5. 圈規 | 從樣板修改：行為準則、引薦禮儀、檢舉流程、移除規則 | 成員加入時需同意 |
| 6. 邀請創始成員 | 貼 email、上傳 CSV、或產生邀請連結（7 天有效、可設人數上限） | 顯示預估寄送時間（受 email 每日額度影響） |
| 7. 預覽與開圈 | 看一眼只有自己一顆星的星圖，按下開圈 | 空狀態也要好看；完成動畫：第一顆星亮起 |

### 7.5 圈主首週清單

- ☐ 自己先完成個人網頁（以身作則）
- ☐ 邀請 ≥ 70% 成員
- ☐ 辦一次 30 分鐘「填資料派對」（線下或線上一起填）
- ☐ 每人至少寫一個牽線標籤
- ☐ 確認第二位管理員能正常登入與操作

**填資料派對 kit**：一份簡報、一張 QR 海報、建議流程（10 分鐘說明 → 15 分鐘一起填 → 5 分鐘一起看星圖亮起來）。這是讓資料一次到位最有效的方式，也是 mass customization 裡「協作式客製」的實際做法。

## 8. 客戶（圈子）維護方式

> v0.3：首圈期間由 Kirby 直接維護；健康度、生命週期等自動化在 P5 才做。

### 8.1 圈主 Console 模組

| 模組 | 圈主能做什麼 |
|---|---|
| 總覽 | 健康度分數、本月成功引薦、待辦（待審入會、待處理檢舉、過期資料） |
| 成員 | 邀請、改角色、移除（需第二位管理員確認）、看誰還沒完成個人網頁 |
| 邀請與擔保 | 成員邀請狀態、擔保紀錄、邀請連結管理 |
| 外圈概況 | 只看聚合數字：外圈總數、本月新增、同意率。看不到誰拒絕了誰 |
| 更新活動 | 一鍵發起半年更新，追蹤完成率 |
| 治理 | 圈規版本（修改需通知成員）、決策紀錄（全體成員可見）、檢舉處理 |
| 設定 | 主題、徽記、入會規則、人數上限、預設可見度 |
| 匯出與交接 | 名錄匯出（只含成員允許的欄位）、圈主轉讓、封存、關閉 |

### 8.2 圈子生命週期

| 狀態 | 進入條件 | 系統動作 | 圈主動作 |
|---|---|---|---|
| 申請中 | 送出申請 | 寄收件確認 | 等待或補件 |
| 設定中 | 核准 | 寄設定連結；7 天未完成提醒一次 | 跑設定精靈 |
| 活躍 | 開圈 | 每月寄圈主月報 | 日常管理 |
| 低頻 | 90 天內沒有成功引薦，也沒有資料更新 | 提醒圈主發起更新或辦聚會 | 發起更新活動 |
| 休眠 | 180 天沒有成員登入 | 寄信問圈主：繼續、交接或封存 | 做決定 |
| 封存 | 圈主選擇，或休眠 365 天未回覆 | 圈子唯讀；外圈收到通知、可選擇退出 | 可隨時恢復 |
| 關閉 | 圈主選擇 | 60 天前通知、提供匯出、到期刪除圈內資料 | — |

個人網頁屬於個人，不受圈子狀態影響。圈子封存或關閉，每個人的 `/@handle` 照樣在。

### 8.3 健康度分數（0–100）

| 組成 | 權重 |
|---|---|
| 資料新鮮度（12 個月內確認過的占比） | 30% |
| 近 90 天成功引薦 | 30% |
| 個人網頁完成度 | 20% |
| 管理員活躍（30 天內登入） | 10% |
| 未處理檢舉（每件扣分） | 10% |

低於 50 分，平台寄關心信並附上建議做法；連續兩個月低於 30 分，平台約圈主聊一次。

### 8.4 平台支援 playbook

- **新圈 onboarding**：試點期每個新圈都有一次 30 分鐘通話，一起跑完設定精靈和首週清單。
- **圈主月報**：每月 1 號寄出，內容包括健康度、本月成功引薦數、經當事人同意的「誰幫了誰」故事、待辦。
- **說明中心**：先用一個公開的 Notion 頁面，收錄常見問題與操作教學。
- **需求看板**：公開的功能地圖（已上線／開發中／規劃中），圈主可以投票。這是參考 HypeLink 的功能地圖。
- **回應時間目標**：一般問題 3 個工作天；個資與安全問題 24 小時；個資申訴依法 30 日內處理完畢，平台目標 7 日。
- **事件溝通**：服務異常或資安事件，依 SOP 通知圈主與受影響的人。

### 8.5 交接、封存與關閉

- **至少 2 位管理員**：系統強制。剩 1 位時，Console 會持續提示補人。
- **圈主轉讓**：需對方接受才生效。
- **圈子交接**：每個圈至少 2 位管理員；首圈的第二位圈主在開圈前確定。
- **平台團隊自己的交接**：網域、Vercel、Supabase、GitHub、Resend 全部放在組織帳號，至少 2 人有管理權限；交接手冊包含架構圖、部署步驟、備份還原演練和個資申訴 SOP。

## 9. 模組化個人網頁

### 9.1 架構：四層組合

```
主題（整體風格：字體、配色、背景、轉場）
 × 版型（單頁捲動／分頁 tabs／卡片牆）
 × 區塊（內容單位，綁定共同資料模型）
 × 可見度（每個區塊各自設定）
 = 每個人獨一無二的網頁，但全部跑在同一套系統上
```

套用 Gilmore & Pine 的四種 mass customization：

| 類型 | 在我們產品裡的樣子 |
|---|---|
| 協作式 | 填資料派對、履歷 PDF 一鍵初稿 |
| 調適式 | 使用者自己換主題、排區塊、設可見度 |
| 外觀式 | 同一份資料輸出成網頁、星、書櫃卡片、QR、LINE 名片 |
| 透明式 | 系統依專長自動把你放進書櫃的對應類別；AI 搜尋時把你排進對的結果 |

### 9.2 區塊目錄

| 區塊 | 內容 | 資料來源 | 預設可見度 | 階段 |
|---|---|---|---|---|
| 主視覺 Hero | 頭像、名字、一句話、標籤 | 個人檔案 | 公開 | MVP |
| 關於 About | 自介 | 個人檔案 | 公開 | MVP |
| 經歷時間軸 Timeline | 學經歷 | 區塊內容 | 公開 | MVP |
| 作品與比賽 Projects | 卡片、圖片、連結 | 區塊內容 | 公開 | MVP |
| 我可以幫你 Offers | 可協助事項 | **書櫃 offers 表** | 我的圈子 | MVP |
| 我正在找 Asks | 目前需求（只出現在自己的網頁，不做公開求救板） | **書櫃 asks 表** | 我的圈子 | MVP |
| 朋友說 Testimonials | 圈內朋友寫的介紹 | testimonials 表 | 我的圈子 | MVP |
| 我的星座 Mini constellation | 以我為中心的小星圖 | edges 表 | 我的圈子 | MVP |
| 連結 Links | 社群與網站連結，可分資料夾；也可連到 HypeLink 等外部品牌頁 | 區塊內容 | 公開 | MVP |
| 聯絡偏好 Contact | 可以直接聯絡，或只接受引薦 | 個人檔案 | 我的圈子 | MVP |

| 相簿 Gallery | 圖片 | 媒體 | 公開 | 後續 |
| 嵌入 Embed | YouTube、Figma、GitHub、Spotify | 區塊內容 | 公開 | 後續 |
| 共同經歷 Shared moments | 和圈友一起做過的事 | shared_experiences 表 | 我的圈子 | 後續 |

關鍵設計：「我可以幫你」和「我正在找」直接讀寫書櫃的資料表。**填網頁就是在填書櫃**，大家不用為了書櫃多填一次。

### 9.3 主題

三套主題（MVP 只上星夜，白紙與作品牆在 P4）：

| 主題 | 感覺 | 適合誰 |
|---|---|---|
| 星夜（預設） | 深藍黑底、細星點背景、✦ 符號、無襯線字體搭配細等寬點綴 | 所有人；也是星圖的視覺延伸 |
| 白紙 | 淺色、大量留白、編輯式排版 | 偏學術、顧問、寫作者 |
| 作品牆 | 卡片格狀、圖片優先 | 設計、攝影、作品集導向 |

- **主題合約**：每套主題是一個 `theme.json`（名稱、版本、支援版型、色彩與字體 token 預設值、可調參數）加上一份 CSS 變數檔。這個做法參考 HypeLink 的主題發布檔，讓主題可以獨立開發與上架；P6 再開放主題 SDK。
- **進階設定**：分頁 tabs、手機底部浮動導覽、轉場與退場動畫、字級。
- **圈子徽記**：成員可以選擇在個人網頁顯示所屬圈子的徽記，預設只有圈友看得到。

### 9.4 網址策略

| 階段 | 網址 | 備註 |
|---|---|---|
| MVP | `<domain>/@handle` | 不需要萬用字元網域，部署最簡單 |
| 後續 | `handle.<domain>` | 需要萬用字元網域與 SSL |
| P6 | 自訂網域 | 個人 Pro 方案【假設】 |

Handle 規則：3–30 字元、英數與底線、保留字清單（admin、console、apply 等）。改名後，舊網址 301 轉址 90 天。

### 9.5 編輯器體驗

- **3 步驟上手**：選主題 → 填主視覺與 3 項「我可以幫你」→ 發布。完成時，你的星在星圖上亮起。
- **擷取管線**（原「履歷 PDF 一鍵初稿」擴充）：資料來源 → 擷取 → 對應到區塊 → 使用者逐項確認 → 寫入。
  - **來源**：(A) 使用者自己的履歷 PDF；(B) LinkedIn「存為 PDF」的檔案（LinkedIn 官方說明此功能限桌機、限檔案語言為英文的會員，S1 spike 實測）。不支援 LinkedIn 資料副本 ZIP。
  - **擷取**：先抽 PDF 文字層（不支援掃描檔），再由 LLM 依區塊 Zod schema 回傳 JSON；伺服器用同一份 Zod 驗證，失敗重試一次，仍失敗就顯示純文字讓使用者手動複製。LLM 不給任何工具或網路權限，履歷文字一律視為不可信輸入。
  - **對應**：姓名、標題 → Hero；摘要 → About；經歷、學歷 → Timeline；專案、獎項 → Projects；技能 → 「我可以幫你」的候選草稿，由使用者改寫後才存。「我正在找」不從履歷推導。
  - **不擷取**：電話、住址、生日、身分證字號、email、推薦人聯絡資料。含他人姓名的句子預設不勾選。
  - **確認**：逐項勾選後才寫入；上傳時勾選「這是我自己的檔案」。
  - **保存**：原檔與抽出的文字處理完立即刪除（失敗也刪）；未確認的草稿最多保留 24 小時；暫存檔每小時清掃。
  - **成本**：【待決】用最便宜的模型（例如 Claude Haiku）、只送文字、固定提示開快取，每人每天限次數。
- **完成度環**：只給自己看，不排名、不給徽章。
- **即時預覽**：手機、電腦切換；「以…身分預覽」可以看訪客和圈友分別看到什麼，讓人對隱私設定有信心。
- **排序**：電腦拖拉；手機用上移、下移按鈕。
- **代建**：給素材，由圈內志工或我們代建。MVP 用填資料派對實現。

### 9.6 渲染與效能

- **公開版**：靜態生成；使用者儲存時即時重新產生（on-demand revalidation）。
- **圈友版**：登入的圈友看到動態渲染的版本，額外帶出圈內可見的區塊。
- **圖片**：上傳前在瀏覽器端壓縮成 WebP（頭像 512px、內容圖 1600px），省掉付費的影像轉換服務。
- **SEO**：【待決，§22 #3】建議公開版預設**不**被搜尋引擎索引，使用者主動開啟；由擷取管線寫入的區塊預設「我的圈子」（§9.2）；自動產生星夜風格的 OG 分享圖。

### 9.7 資料可以帶走

- 公開區塊可匯出成靜態 HTML 壓縮檔，丟到 GitHub Pages 就能繼續用。
- 個人所有資料可匯出 JSON。

## 10. 外圈：同意才出現（雙軌）

### 10.1 狀態機

```
draft    ──送出──▶ pending（寄出 email，14 天有效）
pending  ──同意──▶ accepted（建立外圈身分，出現在圈內）
pending  ──拒絕──▶ declined（刪除 email 原文與介紹內容）
pending  ──第 7 天──▶ 寄一次提醒
pending  ──14 天無回應──▶ expired（刪除規則同 declined）
pending  ──邀請人撤回──▶ revoked
accepted ──本人退出──▶ withdrawn（從圈內移除，刪除圈內資料）
```

邀請人只看得到三種狀態：「邀請中」「已加入」「未加入」。拒絕、過期、撤回一律顯示為「未加入」，避免尷尬。

### 10.2 Email 內容規格

- **寄件人**：「Kirby 透過浮游星」＜noreply@寄信子網域＞
- **主旨**：「Kirby 想把你加入『比賽圈』的星圖」
- **內容順序**：
  1. 邀請人寫給你的一句介紹（最能打動人的部分，放最上面）
  2. 浮游星是什麼（一段話）
  3. 同意後誰會看到什麼：「這個圈子的 15 位成員會看到你的名字、一句話、你可以幫忙的事。這些你都可以改。」
  4. 三個按鈕：同意加入／先看看是什麼／不用了
  5. 個資告知，依《個資法》第 9 條：資料來源、蒐集者、目的、資料類別、利用的期間地區對象與方式、你的權利、不提供的影響
  6. 「不想再收到浮游星的邀請」全域退訂連結
- **同意頁**：不用註冊；可以先編輯要顯示的欄位再按同意；可選填「我的 LinkedIn 網址」（由本人填寫，邀請人不得代填）；同意時記錄告知版本、時間與範圍。打開頁面不改變任何狀態，按下按鈕才以 POST 送出同意（§16.6 一鍵動作）。
- **加入後**：寄確認信，附「管理我的資料」連結，之後用驗證碼登入。
- **需要時才邀的版本**：在介紹語下方加上請求方的需求、時限與「為什麼找你」；同意加入時一併決定要不要接這則引薦。

### 10.3 資料保存規則

| 資料 | 保存期間 | 備註 |
|---|---|---|
| 待回覆邀請的 email 與介紹內容 | 最長 14 天 | 加密儲存 |
| 拒絕、過期或撤回後 | 立即刪除原文 | 只保留 email 的雜湊值（HMAC）6 個月，用來阻擋同圈重複邀請 |
| 全域退訂 | 直到本人取消 | 只保留雜湊值 |
| 同意紀錄 | 關係存續期間，加上退出後 3 年 | 【待法律確認】舉證用 |
| 外圈卡片資料 | 到本人退出或圈子關閉 | 本人可隨時修改或刪除 |

### 10.4 防騷擾規則

- 每位成員在每個圈，同時待回覆的邀請 ≤ 20 則；每天寄出 ≤ 10 則。
- 同一個 email 被拒絕或過期後，同一圈 6 個月內不能再邀。
- 收件人按了全域退訂，任何圈都不能再邀他。
- 某位成員的邀請退信率或檢舉偏高時，自動暫停他的邀請功能，並通知管理員。

### 10.5 外圈同意後能做什麼

- **得到**：一個免費的模組化個人網頁（同一套主題與區塊），以及自己的星光帳本。這是 Matt 按同意的理由之一。
- **看得到**：自己的卡片、邀請人、與自己有連線的成員；圈子開放外圈搜尋時，也能搜尋書櫃（成員可以讓自己對外圈隱藏）。
- **看不到**：其他外圈、圈內的連結故事與朋友說、圈內治理資訊。
- **可以做**：收到引薦請求並決定要不要接；經由邀請他的成員發出引薦請求；修改自己的卡片；隨時退出。
- **多圈**：同一個人可以被不同圈邀請，每個圈分開同意、分開退出。
- **成長路線**：外圈可以 (1) 經擔保升為成員（受人數上限限制），或 (2) 開自己的圈，成為兩個圈之間的第一條關鍵串連（§12.8）。

### 10.6 雙軌：預先邀請＋牽線標籤

v0.2 只有「預先邀請」：Matt 要在還沒有人需要他的時候先按同意，外圈會長得很慢。v0.3 改成兩條路並行：

| | 預先邀請 | 牽線標籤＋需要時才邀 |
|---|---|---|
| 做法 | 成員先寄同意信，Matt 同意後出現在星圖 | 成員在**自己的**檔案寫「我能牽線：碳盤查」；有人提出請求時，才寄附上需求的同意信 |
| 事前存了誰的資料 | Matt 同意後的卡片 | 只有成員自己寫的標籤，**不存 Matt 的任何資料** |
| Matt 為什麼按同意 | 朋友的面子、免費個人網頁 | 有一個具體的人、具體的需求在等他 |
| 適合 | 常被找、願意長期被看見的人 | 偶爾才需要、不想被掛在星圖上的人 |

**牽線標籤規則**

- 標籤寫的是成員自己的能力（「我能幫你找到…」），只用類別描述，不寫第三方姓名、公司或職稱。
- 書櫃搜尋時，牽線標籤和一般 Offer 一起出現，標示為「經由 Kirby 牽線」。
- 請求送到 Kirby 後，他可以：一鍵寄同意信給朋友（附上請求方的需求，§10.2 的告知照樣附上）、自己先私下問，或婉拒。
- 朋友同意後同時完成兩件事：加入外圈、接受這則引薦。
- 標籤 90 天沒確認會提醒本人；連續婉拒 3 次時，提醒本人更新或移除標籤，避免「掛名牽線」。

## 11. 星光與謝禮：讓人情被記得

### 11.1 為什麼不是付費

- 付錢是先開價、再幫忙，那是交易；星光加謝禮是先幫忙、事後感謝，還在人情的範圍。
- 心理學研究（Clark & Mills, 1979）發現，在親近的關係裡把付出和回報算得很清楚，反而會讓彼此疏遠。黃光國的「人情與面子」研究也指出，人情要記得，但不能攤開來算。
- 所以：星光只記在自己心裡（帳本私有），公開的只有感謝的話。

### 11.2 星光怎麼產生

| 星光 | 給誰 | 什麼時候 |
|---|---|---|
| 幫忙星光 | 實際出手幫忙的人 | 引薦結案，請求方回報「有幫助」 |
| 牽線星光 | 轉達的引薦人或橋星 | 同上；跨圈引薦時，每位中間人各一顆 |

- 只在請求方回報「有幫助」時產生，系統不自動判斷。
- 同一對人每月最多產生 2 顆【假設】，防止互刷。
- 星光不能買、不能轉讓、不能換現金，也不影響搜尋排序或誰可以發請求。

### 11.3 誰看得到什麼

| 內容 | 本人 | 對方 | 圈友 | 訪客 |
|---|---|---|---|---|
| 星光帳本（誰幫過我、我幫過誰、次數） | ✓ | ✗ | ✗ | ✗ |
| 感謝語（朋友說） | ✓ | ✓ | 依本人可見度設定 | 依本人可見度設定 |
| 「常牽線的人」小徽記 | ✓ | — | 本人選擇顯示才有 | 本人選擇顯示才有 |
| 謝禮內容 | 送禮人 | 收禮人 | ✗ | ✗ |

### 11.4 一鍵謝禮

- **觸發**：結案頁的「送個謝禮」按鈕；或同一人幫了你 2–3 次、你都還沒表示時，系統私下提醒一次。
- **建議**：只給價位區間（「一杯咖啡」「一頓午餐」），不顯示別人平均送多少。

| 階段 | 做法 | 平台碰錢嗎 | 條件與限制 |
|---|---|---|---|
| 第一階段（P4） | 跳轉 LINE 禮物或品牌的個人送禮頁，使用者自己挑、自己送；回來按「已送出」留紀錄 | 不碰 | 雙方要是 LINE 好友；平台無法確認是否真的送出 |
| 第二階段（P6） | 串接禮券業者，平台代購，對方用簡訊或 email 收券 | 碰 | 需要行號、金流（綠界或藍新）、發票，並和業者談 API |

**可串接對象（2026-10 查詢）**

| 對象 | 現況 |
|---|---|
| LINE 禮物 | 沒查到開放第三方「替使用者送禮」的公開 API，只能跳轉 |
| 宜睿 Edenred 好禮即享券 × LINE | 企業可用 LINE User ID（需自有官方帳號）或手機號碼發券；文章未提到 API |
| 安源資訊 i禮讚（7-ELEVEN 數位商品卡） | 面額可客製，簡訊或 email 發送；對象是企業福委會，2022 年介紹未提到 API |
| GIFQ（全球禮卡 API） | 有 API，含 7-ELEVEN 台灣卡（固定 500 元、限門市使用），價格需洽詢 |

### 11.5 法規底線

- 星光和錢完全脫鉤（不能買、不能轉讓、不能換現金），就不碰《電子支付機構管理條例》的儲值業務。我們沒查到針對這類點數的明確函釋，以上是依條例架構的推論。
- 第二階段平台經手謝禮的錢之前，先請律師確認代收代付與發票的做法。

### 11.6 要防的事

| 風險 | 做法 |
|---|---|
| 兩個好朋友互開假引薦刷星光 | 一定要請求方回報；每對人每月上限；星光不能換錢，動機本來就低 |
| 星光變成開口的門檻（「我星光不夠，不好意思問」） | 星光不影響搜尋排序，也不限制誰可以發請求 |
| 謝禮變成價碼 | 只給價位區間；不公開金額；不讓收禮的人看到別人收了多少 |

## 12. 跨圈與生態系：用人把圈子接成星系

### 12.1 核心命題

- Path 有溫度但沒有觸及，LinkedIn 有觸及但沒有溫度。浮游星要做的是：**溫度留在圈內，觸及靠人跨圈。**
- 每個人本來就同時身在好幾個圈（社會學家 Simmel 稱為「社會圈的交叉」）。同時在兩個圈的人就是天然的橋（Burt 的結構洞），我們叫他們**橋星**。
- 小圈子加入生態系後，人數不變、溫度不變，但經由橋星能觸及的人變多。這是**圈子層級的網路效應**，也是創業上真正的護城河：個人網頁誰都能做（Polywork 的教訓），但經過同意、帶著信任的圈與圈之間的連線，別人抄不走。

### 12.2 星座與星系

- 一個圈＝一個星座；圈與圈之間的正式連線＝星橋；經由星橋相連的圈＝星系。
- 橋星是「人」，星橋是「兩個圈之間的路」。有橋星不代表有星橋。
- 星系圖（P6）以「圈」為單位顯示，不顯示圈外的個人。

### 12.3 跨圈的四條規則

1. **沒有星橋就沒有跨圈。** 兩個圈之間要先開通星橋（§12.4），跨圈搜尋與引薦才會流通。星橋開通前，同時在兩圈的人可以私下幫忙，但平台不替他轉送任何資料。
2. **只能經由人。** 沒有全站搜尋、沒有陌生人名錄。跨圈一定經過一位橋星，或一對跨圈互認的人，由他們決定要不要轉達。
3. **先匿名，同意才具名。** 跨圈搜尋只顯示「在 1 個相連的圈裡有人可能會，經由 Amy」，不顯示名字和圈內細節。對方同意這則引薦後，雙方才看到彼此。
4. **最多 2 位中間人。** 請求方 → 圈內引薦人 → 橋星 → 對方，到此為止。信任隔越多手越淡，太長的路徑不值得打開。

### 12.4 星橋的開通條件

星橋要同時滿足兩個條件才會亮起：**關係夠厚**，而且**兩邊都同意**。

**條件一：關鍵串連數**

關鍵串連是兩圈之間雙方都確認過的真實關係：

| 串連 | 怎麼算 |
|---|---|
| 橋星：同時是兩圈正式成員的人 | 每位 1 條 |
| 跨圈互認：A 圈成員和 B 圈成員互相確認認識 | 每對 1 條 |
| 外圈橋：A 圈的外圈同時是 B 圈成員（例如 Matt 開了 B 圈） | 每位 1 條 |

門檻【假設】：

- **一般星橋**：關鍵串連數 ≥ 3，而且 ≥ 較小那個圈人數的 10%（15 人圈＝3 條，60 人圈＝6 條）。
- **結盟**：門檻加倍。
- **防灌水**：每個人最多貢獻 2 條；兩邊各至少要有 2 位不同的人參與；跨圈互認一定要雙方確認。

為什麼要門檻：只靠一個人撐起來的橋很脆弱，也讓一個人就能把整個圈帶進別的圈。網路研究（Centola & Macy, 2007）指出，需要信任、需要彼此強化的東西，要靠「寬橋」才傳得過去，也就是兩群人之間有多條重疊的關係；一條又細又長的弱連結不夠。引薦正是這種東西。

**條件二：社群投票**

| 項目 | 預設【待決】 |
|---|---|
| 誰投 | 兩個圈的正式成員各自投；外圈不投。同時在兩圈的人，兩邊都投 |
| 投票期 | 7 天 |
| 通過 | 投票率 ≥ 50%，且贊成 ≥ 2/3；圈主可在圈規改成「過半」或「無人反對」 |
| 記名 | 不記名，只公布票數；誰投了什麼，圈主也看不到 |
| 順序 | 提案的圈先投；通過後才通知對方圈主，對方圈主同意後再交給對方全圈投票。對方決定前，不會被公開「誰想跟你們連」 |
| 少數保障 | 任何人都可以選擇「不參與這座星橋」：自己的 Offer 不經這座橋被找到，也不幫忙轉達 |
| 冷卻 | 沒通過的話，同一對圈 90 天內不能再提案 |
| 提案上限 | 每個圈同時最多 2 件星橋提案進行中，避免投票疲勞 |

為什麼要投票：星橋改變的是整個圈的邊界，受影響的人應該參與決定。這是 Ostrom 治理共有資源的原則之一。投票只決定「圈和圈連不連」，不決定「某個人能不能進來」，所以不會變成排擠特定人的工具。

**誰可以提案**：關鍵串連數達到門檻時，系統私下通知兩邊的橋星與圈主，例如：「你們和『永續顧問圈』之間已經有 4 條關鍵串連，要不要提案開星橋？」接著任何成員都可以發起。提案內容包括對方的圈名、一句話介紹、人數區間，以及「開通後會發生什麼」的白話說明。

### 12.5 星橋的生命週期

```
潛在（關鍵串連數達門檻，系統私下提示）
  → A 圈提案、投票（7 天）
  → 通過 → 通知 B 圈主 → B 圈主同意交付投票 → B 圈投票（7 天）
  → 通過 → 開通（星橋亮起）
  → 變暗：關鍵串連數掉到門檻以下（有人退圈、解除互認）→ 通知兩邊圈主
  → 60 天內沒恢復 → 自動關閉
任一方可隨時投票關閉；遇到濫用時，圈主可以緊急暫停，事後再交全圈投票追認
```

- 星橋的開通、變暗、關閉都寫進兩邊的決策紀錄（§8.1），全體成員看得到。
- 星系圖上，星橋的亮度＝關鍵串連數，串連越多越亮。

### 12.6 圈子層級的設定

| 設定 | 選項 |
|---|---|
| 接受星橋提案 | 接受（預設【待決】）／不接受（封閉的圈） |
| 投票規則 | 2/3（預設）／過半／無人反對 |
| 星橋等級上限 | 一般星橋／可結盟 |

- **一般星橋**：只流通匿名的「有人可能會」，經由人轉達。
- **結盟**：門檻加倍、兩邊都要通過；成員可以讓自己的 Offer 對結盟圈具名可見。
- **成員層級**：每項 Offer 可以設定「跨圈可被找到（匿名）」；外圈的資料預設**不參與跨圈**，要他自己打開，因為他當初只同意了一個圈。

### 12.7 匿名也可能洩漏身分

相連的圈如果只有一個人會「水下攝影」，「有人可能會」就等於指名道姓。所以：

- 跨圈結果只顯示「有／沒有」，不顯示人數。
- 搜尋詞太細時，合併到上一層類別再比對。
- 同一位使用者對同一類別的跨圈查詢有次數上限，避免用排除法猜人。

### 12.8 生態系怎麼長：飛輪

```
外圈 Matt 同意加入 A 圈
  → 拿到免費個人網頁、可以搜尋 A 圈書櫃、累積星光與感謝
  → 想把自己的朋友也接進來
  → 開自己的 B 圈（成為 A、B 之間的第一條關鍵串連）
  → 兩圈的關係慢慢變厚 → 串連數達門檻 → 兩邊投票 → 星橋亮起
  → B 圈的外圈又開 C 圈……
```

- **每個新圈出生時就帶著一條關鍵串連**：創圈的人一定來自既有的圈（成員或外圈），所以新圈天生就有機會連上星系；但一條不夠，要長到夠厚、兩邊都願意，星橋才會開。
- 對照 Facebook 早期：它用學校網域劃牆，一校一校開放；浮游星用人劃圈，也用人接圈。
- 飛輪指標：新圈中，創圈者原本就在某個圈的比例（§3.3）。

### 12.9 橋星：生態系的關鍵少數

- 橋星做跨圈轉達時得到牽線星光（§11），可以選擇顯示「常牽線的人」小徽記。
- 橋星最容易被消耗：每月轉達上限可以自己設；被請求太頻繁時，系統先建議同圈的其他橋星。
- 圈主 Console 顯示這個圈有幾位橋星、開通了幾座星橋，以及每座星橋的關鍵串連數（只看數量）。

### 12.10 生態系層級的產品

| 產品 | 說明 | 階段 |
|---|---|---|
| 圈主圈 | 所有圈主組成的交流圈，分享填資料派對、圈規怎麼寫 | P6 |
| 結盟活動 | 兩個結盟圈一起辦線下活動（例如比賽組隊交流），把橋變粗 | P6 |
| 星系圖 | 以圈為單位的地圖，只顯示已開通的星橋與同意被看見的圈；星橋亮度＝關鍵串連數 | P6 |
| 跨圈主題市集 | 主題設計師的作品在所有圈通用 | P6 |

### 12.11 現成的試點

- **比賽圈＋全屆圈**：兩個圈天然重疊，比賽圈的 15 人幾乎都會是橋星。關鍵串連數一開始就遠超門檻，可以專心測投票流程，是第一座星橋最好的候選。
- **Toastmasters 的大學社團**：一組現成、彼此有交集的圈，適合 P5 測試結盟與跨圈。仍是一圈一圈邀請，不是賣給組織。
- **外圈開新圈**：P5 的試點圈優先從首圈的外圈裡找，直接驗證飛輪。

### 12.12 生態系的風險

| 風險 | 緩解 |
|---|---|
| 生態系慢慢變成 LinkedIn | 四條規則寫死在產品裡：沒有星橋就沒有跨圈、只能經由人、先匿名、最多 2 位中間人；不做全站搜尋 |
| 有人開假圈收集人脈（招募、直銷） | 開圈審核；星橋要關鍵串連數與兩邊投票；跨圈一定要有人轉達；婉拒率高的星橋自動變暗 |
| 有人灌水關鍵串連，想硬開星橋 | 互認要雙方確認；每人最多貢獻 2 條；兩邊各至少 2 位不同的人 |
| 星橋投票造成圈內對立 | 不記名、只公布票數；少數可以不參與；未通過冷卻 90 天；投票只決定圈與圈，不決定個人去留 |
| 匿名結果洩漏身分 | 只顯示有／沒有、類別合併、查詢次數上限（§12.7） |
| 橋星被消耗 | 轉達上限、分流到其他橋星、牽線星光 |
| 外圈的同意範圍被擴大解釋 | 外圈預設不參與跨圈，要自己打開 |

## 13. 設計方向與 HypeLink 借鏡

### 13.1 視覺方向「星夜」

- **深色為預設**，星圖、個人網頁、Console 共用同一套設計 token。
- **✦ 作為品牌符號**，剛好呼應「浮游星」。用在按鈕前綴、分隔、載入動畫、徽記。
- **雙語層次**：英文小標配中文大標，例如「Your Circle／你們的星圖」。
- **跑馬燈分隔帶**：例如「✦ 想得到 ✦ 找得到 ✦ 請得動 ✦」，用在官網與開圈頁。
- **動態**：星的漂浮用緩慢柔和的力導向；拖拉與按鈕回饋用彈簧緩動（spring）；完成動畫是星星亮起，不是撒彩帶。
- **空狀態也要好看**：只有一顆星的星圖、還沒有 Offer 的書櫃，都要有設計過的畫面。
- **字體**：中文 Noto Sans TC（思源黑體），英文 Inter 一類的無襯線，等寬字體做點綴。

| HypeLink 的做法 | 為什麼不學 |
|---|---|

# Part 2｜開發方案

## 14. 開發方案總覽

### 14.1 開發原則

1. **權限寫在資料庫，不寫在畫面上。** 所有可見度規則都由 Postgres 的 Row Level Security（RLS）執行。前端只是把東西藏起來，不算保護。
2. **可見度以「列」為單位。** 每個能單獨設定可見度的東西（一個區塊、一項「我可以幫你」、一種聯絡方式）都是一列資料。RLS 只管得到列，所以資料表一開始就要切好。
3. **service role 金鑰只出現在三個地方**：Edge Functions、排程工作、不需登入的 token 端點（外圈同意頁、email 一鍵動作）。其他查詢一律用使用者自己的身分。
4. **主流、無聊、好交接。** 選學生最容易接手的技術，每個重要決策寫一頁 ADR（Architecture Decision Record）。
5. **先人工，後自動。** P1 用人工媒合驗證流程有效，才寫成程式。
6. **免費額度跑得動。** 首圈全年成本壓在新台幣 2,000 元內，每項服務都寫好「超出額度時怎麼辦」。
7. **一個人也顧得動。** Kirby 用 AI 單人開發，每週 10–20 小時。一個人顧不來的功能就延後，不硬做。

### 14.2 系統架構

```
使用者（手機瀏覽器／LINE 內建瀏覽器／桌機）
   │
   ▼
Next.js（App Router，部署在 Vercel，Functions 設東京 hnd1）
 ├─ 公開個人網頁  /@handle → /u/[handle]   靜態生成＋儲存時即時重新產生
 ├─ 圈內 App      /c/[circle]/...           星圖、書櫃、引薦、星光
 ├─ 個人設定      /me/...                   編輯器、通知、匯出

   ▼

 ├─ Auth：Email 6 位數驗證碼（自訂 SMTP＝Resend）

```

## 15. 前端方案

### 15.1 路由與渲染

| 路由 | 給誰 | 渲染方式 |
|---|---|---|
| `/`、`/apply`、`/apply/status` | 訪客、申請者 | 靜態／動態 |
| `/@handle`（rewrite 到 `/u/[handle]`） | 所有人 | 公開版：靜態生成，儲存時即時重新產生；登入的圈友：動態渲染，多帶出圈內區塊 |
| `/c/[circle]` | 成員 | 星圖，client 端繪製 |
| `/c/[circle]/shelf`、`/asks`、`/intros/[id]` | 成員 | 動態 |
| `/me/page`、`/me/settings`、`/me/notifications`、`/me/export` | 本人 | 動態 |
| `/invite/[token]` | 成員邀請、外圈同意 | 動態，不需登入 |
| `/a/[token]` | 引薦人、外圈 | email 一鍵動作（同意、婉拒、轉達），簽章 token，不需登入 |
| `/console/[circle]/...` | 圈主、管理員 | 動態（路由見 §7.6） |
| `/admin/...` | 平台 | 動態 |

注意：App Router 裡 `@` 開頭的資料夾是平行路由（parallel routes）的保留語法，所以 `/@handle` 不能直接當資料夾名稱。做法是在 `next.config` 加 rewrite，把 `/@:handle` 導到 `/u/:handle`。

### 15.2 星圖實作

- **資料**：`get_constellation(circle_id)` 回傳已套用可見度與封鎖規則的節點與連線，前端不再判斷權限。
- **佈局**：d3-force 的 `forceRadial` 把成員拉到內圈、外圈連結拉到外圈，再加上連線力與碰撞力。同一位外圈被多位成員認識時，會自然落在這幾位成員之間。
- **繪製**：react-force-graph-2d 的 Canvas 模式，用自訂 `nodeCanvasObject` 畫星：光暈、亮度（資料新鮮度，見 M4-5【待決】）、圈子徽記色。
- **漂浮感**：力模擬收斂後就停止（省電），漂浮改成繪製時的微小正弦位移；使用者開啟「減少動態效果」時關閉。
- **互動**：點星開卡片；書櫃搜尋結果在星圖上高亮「我 → 引薦人 → 對象」的路徑；「我的星座」只取 2 度以內的子圖。
- **效能預算**：600 顆星在中階手機維持 30 fps 以上。超過 1,000 顆時再評估改用 sigma.js（WebGL）。
- **無障礙**：列表模式和星圖讀同一份資料；鍵盤可以逐顆巡覽。
- **海報匯出（P4）**：在離屏 Canvas 以 4 倍解析度重繪，輸出 PNG；PDF 用列印樣式表。

### 15.3 區塊系統（`packages/blocks`）

每個區塊都用同一個 `defineBlock()` 定義，內容包括：型別、版本、標籤、資料來源、預設可見度、設定的 Zod schema、渲染元件、編輯元件。範例見附錄 C。

- **兩種區塊**：
  - **內容型**（Hero、About、Timeline、Projects、Links、Rich text）：資料存在 `blocks.content`（JSONB）。
  - **綁定型**（Offers、Asks、Testimonials、Mini constellation、Contact）：`blocks` 只存設定（標題、顯示幾項），資料從對應資料表讀。**填網頁就是在填書櫃**，在程式上就是這樣實現的。
- **實際可見度**＝區塊可見度與單項可見度取較嚴格的那個。例如「我可以幫你」區塊設為公開，但其中一項設為「我的圈子」，訪客就看不到那一項。
- **版本遷移**：`content` 內含 `v`。區塊改版時寫 `migrate(v1 → v2)`，讀取時自動升級，不用一次改全部資料。
- **同一套元件**：公開頁、圈友版、編輯器預覽都用同一個 `Render`，確保所見即所得。

### 15.4 主題系統（`packages/themes`）

- 每套主題一個資料夾：`theme.json`（合約，範例見附錄 B）＋`tokens.css`＋選配的元件覆寫（例如作品牆的 Hero 變體）。
- 頁面儲存「主題 id、版本、參數值」。伺服器渲染時把參數注入成 CSS 變數，主題不需要額外的 JavaScript。
- **字型**：Noto Sans TC 透過 `next/font` 載入；Google Fonts 會把中文字型切片、按需下載，不會一次載入幾 MB。
- **主題版本**：不相容的變更升主版號，舊版保留，不會讓別人的網頁突然跑版。

### 15.5 編輯器

- **左右分割**：左邊依區塊分段的表單，右邊即時預覽。手機版改成上下切換。
- **以…身分預覽**：在伺服器端用模擬的觀看者身分（訪客、圈友、指定圈子）跑同一個可見度過濾函式，不是用 CSS 藏起來，所以預覽看到的就是真實結果。
- **儲存模式**：MVP 不做草稿版本，儲存即生效；第一次按「發布」前，公開網址回傳 404。草稿與版本紀錄放後續。
- **擷取管線**（§9.5）：
  1. 上傳到私有的 `uploads` bucket（限 PDF、5 MB；拒收 ZIP）。
  2. Edge Function 抽出文字層（MVP 不支援掃描檔）。
  3. LLM 依區塊 Zod schema 回傳 JSON 草稿，略過身分證字號、住址、電話、email、生日，並標記疑似他人姓名；不給 LLM 任何工具或網路權限。伺服器以同一份 Zod 驗證，失敗重試一次，再失敗改顯示純文字。
  4. 使用者逐項勾選後才寫入；含他人姓名者預設不勾選。
  5. 原檔與抽出的文字在處理完成後立即刪除（失敗也刪）。

### 15.6 效能與品質預算

| 項目 | 目標 |

### 16.3 狀態機

**引薦請求**

```
sent_to_broker ──引薦人同意轉達──▶ sent_to_target
sent_to_broker ──引薦人婉拒／逾期──▶ not_connected
sent_to_target ──對象同意──▶ connected（雙方拿到彼此選擇公開的聯絡方式）
sent_to_target ──對象婉拒／逾期──▶ not_connected
（圈內成員之間的直接請求，從 sent_to_target 開始）
connected ──請求方回報──▶ closed
connected ──第 7 天──▶ 寄結案回報邀請；30 天沒回報 → closed（無回報）
任何等待狀態 ──請求方撤回──▶ withdrawn
```

- 每個等待步驟的時限是「72 小時」和「請求方需要的日期」取較早的；第 48 小時寄一次提醒。
- 請求方只看到「進行中」「已連上」「這次沒成功」三種狀態。婉拒和逾期不區分，原則與外圈邀請相同。
- 「這次沒成功」的通知會附上書櫃裡的其他路徑，讓請求方馬上有下一步。
- 每次狀態變更都寫一筆 `intro_events`，北極星指標和漏斗都從這裡算。

**牽線標籤與跨圈的變體**

```
牽線標籤：sent_to_broker ──引薦人寄附需求的同意信──▶ awaiting_consent ──朋友同意加入並接受──▶ connected
跨圈：    sent_to_broker ──圈內引薦人轉達──▶ sent_to_bridge ──橋星轉達──▶ sent_to_target ──對方同意──▶ connected
```

- `awaiting_consent` 沿用外圈邀請的 14 天期限；請求方的時限較短時，以較短者為準。
- 跨圈請求在對方同意前，請求方只看到「經由 Amy」，看不到對方是誰；對方只看到需求內容與請求方的公開卡片。
- 跨圈請求只能走已開通（含變暗中）的星橋；選擇不參與該星橋的人，不會出現在路徑上。
- 結案回報「有幫助」時，依路徑上的角色產生星光（§11.2）。

**成員入會（提名加擔保制）**

```
nominated ──擔保人數達標──▶ pending_admin ──管理員核准──▶ invited ──接受邀請、同意圈規──▶ active
```

外圈邀請的狀態機見 §10.1。

### 16.4 書櫃搜尋

```sql
search_shelf(p_circle uuid, p_query text, p_limit int default 20)
returns table (offer_id uuid, person_id uuid, is_external boolean, via_ids uuid[], score real)
```

1. 確認呼叫者是這個圈的內圈成員（`active`、非 `external`）。
2. 候選：圈內成員與已同意外圈的 Offer，可見度通過，而且雙方都沒有封鎖對方。
3. 比對：標籤完全命中（含同義詞展開）權重最高，PGroonga 全文比對其次；P5 加上向量相似度。
4. 外圈結果附上 `via_ids`，也就是跟他有連線的成員（可能的引薦人），並排除封鎖呼叫者的人。
5. 公平排序：分數相同時隨機排（以「使用者＋日期」為種子，翻頁時結果穩定）；近 30 天收到請求最多的前 10% 成員稍微降權；超過 12 個月未確認的資料降權（後續）。
6. 隱私：一般查詢只記錄次數與結果數，不存查詢原文，因為需求內容可能很私密。只有零結果的查詢原文保留 30 天，用來補標籤同義詞。
7. **牽線標籤**：和 Offer 一起比對，結果標示「經由某某牽線」。
8. **外圈呼叫時**：圈子開了 `externals_can_search` 才能搜，並排除 `hide_from_externals` 的 Offer。
9. **AI 搜尋（P3，低成本版，ADR 0001）**：先跑一般比對；結果少於 3 筆時才出現「讓 AI 幫我找」按鈕，使用者按下才呼叫 LLM。LLM 只能從圈內現有的標籤清單挑選，把自然語言需求改寫成標籤與關鍵字，再走上面的比對。AI 只負責找與排序，不主動通知任何人。
   - 成本：用最便宜的模型等級（例如 Claude Haiku）；同一句查詢 30 天內重用結果（快取以雜湊為鍵，不存原文）；每人每天 20 次；LLM 帳號設每月消費上限。
   - 隱私：查詢文字會送到 LLM 服務，隱私權政策要揭露；只送呼叫者看得到的標籤清單。
   - 工時粗估 6–8 小時；不夠時整個砍掉，退回關鍵字＋同義詞（§18.5 第 4 順位）。
10. **跨圈（P5）**：另一支 `search_bridges(p_circle, p_query)`，只搜尋已開通的星橋，只回傳「哪座星橋、經由誰有符合」的布林值，不回傳人；排除選擇不參與該星橋的人；類別過細時往上合併（§12.7）。

### 16.6 Email 系統

- **寄信網域**：用子網域（例如 `mail.<domain>`），設好 SPF、DKIM、DMARC。Gmail 與 Yahoo 從 2024 年起對寄件驗證要求變嚴，沒設好很容易進垃圾信匣。
- **Auth 驗證信**也走 Resend SMTP。
- **樣板**：React Email，清單見附錄 D。中文主旨避開行銷字眼。
- **一鍵動作**：引薦人收到的信裡有簽章 token（一次性、72 小時有效），不用登入就能同意、婉拒或轉達；外圈邀請的 token 效期依 §10.1。**連結只開啟確認頁，GET 不改變任何狀態，按下頁面按鈕才以 POST 執行，避免信件掃描器預取造成誤同意。**
- **送達監控**：Resend webhook（送達、退信、投訴）寫回 `events`。某位成員的邀請退信率偏高時，自動暫停他的邀請功能（§10.4）。
- **額度管理**：批次邀請進佇列，依方案的每日上限寄出，Console 顯示預估完成時間。全屆上線那個月，建議改用邀請連結搭配填資料派對，省下寄信額度；真的不夠就臨時升級一個月。

## 17. 權限、隱私與資安工程

### 17.1 RLS 核心函式與政策（節錄）

```sql
-- 目前登入者在 people 表的 id
create function me() returns uuid
language sql stable security definer set search_path = public as $$
  select id from people where auth_user_id = auth.uid()
$$;

-- viewer 是否和 owner 同在某個圈，且 viewer 是內圈成員
create function shares_circle(viewer uuid, owner uuid) returns boolean
language sql stable security definer set search_path = public as $$
  select exists (
    select 1
    from memberships v
    join memberships o on o.circle_id = v.circle_id
    where v.person_id = viewer and v.status = 'active' and v.role <> 'external'
      and o.person_id = owner  and o.status = 'active'
  )
$$;

-- 任一方封鎖另一方
create function blocked_between(x uuid, y uuid) returns boolean
language sql stable security definer set search_path = public as $$
  select exists (
    select 1 from user_blocks
    where (blocker_id = x and blocked_id = y) or (blocker_id = y and blocked_id = x)
  )
$$;

alter table blocks enable row level security;

create policy blocks_select on blocks for select using (
  visibility = 'public'
  or person_id = (select me())
  or (
    not blocked_between((select me()), person_id) and (
      (visibility = 'circles' and shares_circle((select me()), person_id))
      or (visibility = 'selected' and exists (
        select 1 from memberships v
        where v.person_id = (select me()) and v.status = 'active' and v.role <> 'external'
          and v.circle_id = any (blocks.visible_circle_ids)))
    )
  )
);

create policy blocks_write on blocks for all
  using (person_id = (select me()))
  with check (person_id = (select me()));
```

- `(select me())` 的寫法讓 Postgres 每次查詢只算一次，這是 Supabase 建議的 RLS 效能寫法。
- `visible_circle_ids` 只能填本人所屬的圈，由寫入時的 trigger 檢查。
- 公開區塊另外要求該頁已發布（`pages.published_at` 不為空）。
- `offers`、`asks`、`testimonials`、`contact_methods` 用同一套模式。聯絡方式多一條：存在 `intro_contact_grants`（引薦連上）時，對方才看得到。

### 17.2 封鎖的效果與限制

- **被封鎖的人**：看不到你的圈內內容；星圖上沒有你；書櫃搜尋不到你；不能對你發引薦或邀請。
- **限制**：公開區塊本來就對任何人開放，封鎖擋不住。設定頁要直接寫清楚：「不想讓特定的人看到的內容，請設成『我的圈子』」。

### 17.3 個資保護措施（對應《個資法》）

| 條文 | 做法 |
|---|---|
| 第 9 條 間接蒐集告知 | 外圈邀請信附完整告知；告知文字有版本號，同意時記錄版本 |
| 第 19、20 條 蒐集與利用 | 外圈：當事人同意；成員：服務條款加同意。只在告知的目的內利用 |
| 第 3 條 當事人權利 | 自助查看、修改、匯出（JSON）、刪除；其他申請寄到專用信箱 |
| 第 27 條 安全維護 | RLS、加密、最小權限、稽核紀錄、備份加密、事件應變 SOP |
| 2025 年修法（外洩通報等） | 先備好外洩應變 SOP 與通報範本；施行日期【需確認】 |
| 跨境傳輸 | 資料庫在東京，LLM 與 email 服務在境外，都寫進隱私權政策 |
| 牽線標籤 | 只寫成員自己的能力類別，不存第三方資料 |
| 擷取管線（履歷、LinkedIn PDF） | 只處理使用者本人上傳的本人資料；推薦人、同事等第三人資料預設不匯入；告知寫入隱私權政策與上傳畫面；LLM 在境外（同跨境列）；原檔即刪 |
| 需要時才邀 | 朋友的 email 只在寄出同意信時暫存，規則同 §10.3 |

### 17.4 加密與金鑰

- 傳輸一律 TLS；資料庫靜態加密由 Supabase 提供。
- 待回覆邀請的 email：應用層 AES-256-GCM 加密，金鑰放在 Edge Function 的環境變數；進入終局狀態立即清空。
- Email 雜湊：HMAC-SHA256，金鑰獨立保存。
- 所有 token 只存雜湊，一次性、有期限。
- 備份：age 加密後上傳；解密金鑰只存在 2 位管理員的密碼管理器裡。

### 17.5 刪除流程

| 情況 | 處理 |
|---|---|
| 刪除帳號 | 立即下架個人網頁、退出所有圈；7 天反悔期後永久刪除資料與檔案；備份中的副本隨 4 週輪替消失（隱私權政策寫明） |
| 外圈退出某圈 | 立即移除該圈的卡片、連線、書櫃條目；同意紀錄依 §10.3 保存 |
| 圈子關閉 | 60 天通知期後刪除圈內資料（連線、故事、我正在找、引薦紀錄、星光）；個人網頁不受影響 |
| 引薦紀錄中的已刪除者 | 顯示為「已刪除的使用者」，保留統計所需的匿名事件 |

### 17.6 稽核與上線前資安檢查

- `audit_logs` 記錄：角色變更、移除成員、名錄匯出、平台人員查看圈內資料（必填原因）、圈設定變更。
- **外部檢查**：Kirby 單人開發，所以第一次開放外圈功能前，請一位懂資安的工程師做獨立檢查，重點是 RLS、不需登入的 token 端點與外圈資料。CN 擔任架構顧問，資料模型的重大變更先給她看。**檢查分兩段：S8 外圈預先邀請對首圈開放前，先做範圍小的檢查（RLS、`/invite/[token]`、`/a/[token]`、外圈資料）；S13 再做完整檢查。S8 前沒完成第一段，外圈功能只對測試帳號開放。**
- 上線前檢查清單：
  - CI 檢查每張 public schema 的表都開了 RLS
  - service role 使用點只有 §14.1 的三處
  - 所有 token 都有期限
  - 上傳檔案限制類型與大小
  - 速率限制生效
  - Dependabot 相依套件掃描
  - Supabase Security Advisor 沒有警告

## 19. 收費模式假設

**原則**

- 被找到、被看見，永遠免費；不向招募方或任何第三方收錢「看人」。
- 不替幫忙開價。平台的錢只來自「感謝」和「門面」，不來自「交易」。
- 資料匯出永遠免費（產品原則 6）。
- P5 以前全部免費；P6 才實驗收費，而且要先有行號與金流。

| 收入 | 說明 | 階段 | 價格假設 |
|---|---|---|---|
| 謝禮抽成 | 一鍵謝禮第二階段：平台代購禮券，賺通路價差或手續費 | P6 | 每筆 5–10%【假設】 |
| 個人 Pro | 自訂網域、進階主題、相簿與嵌入不限量 | P6 | 每年 NT$ 600–900【假設】 |
| 圈子紀念品 | 星圖海報印刷、NFC 星卡、年度圈子星圖冊 | P4 起以成本價試做，P6 才營利 | 星卡每張 NT$ 150–250、海報 NT$ 300–600【假設】 |
| 主題市集 | 設計師上架主題，平台拆帳 | P6 | 每套 NT$ 90–300【假設】 |

**為什麼謝禮抽成最有潛力**：它跟著「幫忙真的發生」一起成長。星系越大、跨圈引薦越多，謝禮就越多；而且錢來自感謝，不會讓任何人變成被標價的商品。

**開始收費前要處理的事**

- Vercel Hobby 限非商業用途，收費後要升級 Pro【需確認】。
- 金流：Stripe 目前應不支援台灣商家，考慮綠界（ECPay）或藍新（NewebPay）【需確認】；需要公司或行號，並開立電子發票。
- 謝禮第二階段涉及代收代付，先請律師確認是否觸及電子支付相關規範。
- 外圈的個資告知要加上商業用途；服務條款與隱私權政策改版。
